**Omega-check** เป็นเครื่องมือแบบ TUI + CLI ที่สแกนพอร์ตของเป้าหมายเครือข่ายเดียว ระบุบริการที่ทำงานบนแต่ละพอร์ตที่เปิดอยู่ (โปรโตคอล ซอฟต์แวร์ เวอร์ชัน การยืนยันตัวตน WAF TLS) และอนุมานบทบาทที่น่าจะเป็น โดยไม่ทำการโจมตีเชิงรุกใด ๆ เลย เป็นเครื่องมือหนึ่งในชุด `omega-` จัดโครงสร้างตาม Clean Architecture — รายละเอียดทางเทคนิคทั้งหมดดูที่ `docs/ARCHITECTURE.md`

## 1. วิสัยทัศน์และขอบเขต

Omega-check เป็นเครื่องมือสแกนพอร์ตสำหรับงานดูแลระบบ: ตรวจอย่างรวดเร็วว่ามีอะไรรอรับการเชื่อมต่ออยู่บนเครื่อง (เครื่องของคุณเอง ใน LAN หรือเป้าหมายภายนอกที่ได้รับอนุญาต) ด้วยอะไร และแต่ละข้อมูลเชื่อถือได้มากน้อยเพียงใด

### สิ่งที่ Omega-check ทำ

- สแกนรายการพอร์ต (โปรไฟล์ระบบ โปรไฟล์ส่วนตัว หรือกรอกเอง) บนเป้าหมายเดียว
- ระบุบริการบนแต่ละพอร์ตที่เปิดอยู่: โปรโตคอล (HTTP/HTTPS/SSH/TLS/VNC/ทั่วไป) ซอฟต์แวร์และเวอร์ชันเมื่อเปิดเผย และความจำเป็นในการยืนยันตัวตน
- อนุมานบทบาทที่น่าจะเป็น (เว็บเซิร์ฟเวอร์ การเข้าถึงเชลล์ การเข้าถึงแบบกราฟิก ฐานข้อมูล) จากโปรโตคอลที่เจรจาได้จริง ไม่ใช่แค่การเดาจากหมายเลขพอร์ต
- ตรวจพบลายเซ็น WAF ที่รู้จัก (Cloudflare, Sucuri, Akamai, Imperva Incapsula) เมื่อมีการประกาศไว้ในส่วนหัว
- แสดงผลใน TUI (Textual) หรือ CLI ที่เขียนสคริปต์ได้ และส่งออกได้สามแบบ: JSON ข้อความ HTML (5 ธีม)
- ระบุระดับความเชื่อมั่นที่ชัดเจนให้กับทุกข้อมูลที่เก็บได้ — ดู [§7](#7-นโยบายความเชื่อมั่น)
- เก็บประวัติการสแกนถาวร เรียกซ้ำและเปรียบเทียบข้ามเวลาได้
- ปักหมุดเป้าหมายและสร้างโปรไฟล์พอร์ตส่วนตัวได้ ใช้ซ้ำได้ทุกครั้งที่สแกน

### สิ่งที่ Omega-check ไม่ทำ

- สแกนช่องโหว่เชิงรุก: ไม่มี SQLi, XSS หรือ RCE
- สแกน CVE
- ระบุระบบปฏิบัติการ (แบบจำลองข้อมูลเตรียมช่องไว้แล้ว แต่ยังไม่มีฮิวริสติกใดกรอกข้อมูล)
- เทคนิคสแกนระดับล่างแบบ nmap (SYN scan, แพ็กเก็ตดิบ) — ใช้เฉพาะการเชื่อมต่อ TCP ระดับแอปพลิเคชัน
- เครื่องมือ brute force หรือฟัซซิง
- สแกนหลายเป้าหมายพร้อมกัน
- แดชบอร์ดเว็บ

## 2. การติดตั้ง

### ข้อกำหนดเบื้องต้น

- Python 3.10+
- การเชื่อมต่ออินเทอร์เน็ต สำหรับติดตั้งส่วนที่ต้องพึ่งพา

### การติดตั้ง

```bash
[ -d omega-check ] && echo "ℹ️ แตกไฟล์ไว้ที่นี่แล้ว ข้ามขั้นตอนนี้" || tar -xzf omega-check.tar.gz
cd omega-check/
chmod +x install.sh
./install.sh
```

`install.sh`:

1. สร้างสภาพแวดล้อมเสมือน `.venv` หากยังไม่มี
2. ติดตั้งส่วนที่ต้องพึ่งพา (`pip install -e .`; `pyproject.toml` ยังคงเป็นแหล่งข้อมูลหลักเพียงแหล่งเดียว)
3. ทำให้ `omega-check.sh` และ `install.sh` เรียกใช้งานได้
4. เพิ่มชื่อแทน `check` ลงใน `~/.bashrc` และ `~/.zshrc` (ไม่เพิ่มซ้ำหากมีอยู่แล้ว)

### ส่วนที่ต้องพึ่งพา

ประกาศไว้ใน `pyproject.toml` (ไม่มี `requirements.txt` แล้ว):
- `omega-lib`: ไลบรารีที่ใช้ร่วมกันของชุดเครื่องมือ (`ConfidenceLevel` ธีม การตรวจจับเทอร์มินัล)
- `textual`: อินเทอร์เฟซ TUI ธีม และการปรับให้เข้ากับเทอร์มินัลโดยอัตโนมัติ
- `httpx`: ตัวตรวจ HTTP/HTTPS
- `cryptography`: อ่านใบรับรอง TLS ที่เจรจาได้
- `jinja2`: เทมเพลตสำหรับการส่งออก HTML
- ส่วนที่ต้องพึ่งพาสำหรับการพัฒนา (`pip install -e ".[dev]"`): `pytest`, `pytest-asyncio`, `pytest-cov`, `pytest-httpserver`, `trustme`, `ruff`, `mypy`, `import-linter`

## 3. การใช้งาน

### โหมดโต้ตอบ (TUI)

แนะนำสำหรับการใช้งานประจำวัน — เรียกโดยไม่ใส่อาร์กิวเมนต์:

```bash
./omega-check.sh
```
หากสร้างชื่อแทนไว้แล้ว เพียงพิมพ์ `check` ในเทอร์มินัล:
```bash
check
```

ลำดับการใช้งาน: หน้าจอเริ่มต้น (ปิดด้วยการกดปุ่มหรือคลิก) → เมนูหลัก (สแกน / เป้าหมาย / โปรไฟล์ / ประวัติ / การตั้งค่า / ช่วยเหลือ) → กรอกเป้าหมาย (เลือกจากเป้าหมายที่ปักหมุดได้) และเลือกโปรไฟล์ (มีคำเตือนเมื่อเลือก `complet` และมีช่องที่สองสำหรับโปรไฟล์ส่วนตัวหรือกรอกพอร์ตเองเมื่อเลือก `CUSTOM`) → การสแกน (แถบความคืบหน้าแบบไม่ระบุและบันทึกการทำงานเครือข่ายสด) → รายละเอียดการสแกน (พอร์ต/บริการ/บทบาท การส่งออก) → ประวัติ/การเปรียบเทียบ/การเรียกซ้ำ และการตั้งค่าจากเมนูหลัก การปรับให้เข้ากับเทอร์มินัล (สี ขนาด การลดทอนโครงสร้าง) เป็นไปโดยอัตโนมัติ

#### แป้นลัด

| แป้น | การทำงาน |
|---|---|
| `↑` / `↓` | เลื่อนไปมาระหว่างรายการบนหน้าจอ |
| `Tab` / `Shift+Tab` | เลื่อนไปมาระหว่างช่องของแบบฟอร์ม |
| `Esc` | กลับไปหน้าจอก่อนหน้า (ยืนยันการออกเมื่ออยู่ที่หน้าแรก) |
| `t` | ธีมถัดไป (ใช้ทันที ไม่ต้องยืนยัน) |
| `r` | รีเฟรชการตรวจจับเทอร์มินัล |
| `a` | แสดงความช่วยเหลือ |
| `q` | ออก (ต้องยืนยัน) |

### ภาษาของอินเทอร์เฟซ

อินเทอร์เฟซมีให้ใช้ 17 ภาษา: ฝรั่งเศส อังกฤษ สเปน โปรตุเกส (บราซิล) อิตาลี เยอรมัน ดัตช์ โปแลนด์ รัสเซีย จีนตัวย่อ เวียดนาม ไทย อินโดนีเซีย ญี่ปุ่น เกาหลี ฮินดี และอาหรับ เลือกได้ในการตั้งค่า (“Langue / Language”) และมีผลหลังจากรีสตาร์ตอินเทอร์เฟซ ตัวแปร `OMEGA_CHECK_LANG` (เช่น `OMEGA_CHECK_LANG=th ./omega-check.sh`) ใช้บังคับภาษาสำหรับหนึ่งเซสชัน เมื่อเปิดจาก omega-suite แล้ว omega-check จะใช้ภาษาของชุดเครื่องมือ บนคอนโซลข้อความของ Linux (TTY) ภาษาที่ไม่ได้ใช้อักษรละตินจะแสดงเป็นภาษาอังกฤษตลอดเซสชันนั้น บรรทัดคำสั่งยังคงเป็นภาษาฝรั่งเศส

### โหมดสคริปต์ (CLI)

คำสั่งย่อยใดก็ตามจะเปิดโหมด CLI:

```bash
# สแกนเป้าหมายด้วยโปรไฟล์พอร์ต
./omega-check.sh scan 192.168.1.10 --profile minimal

# ประวัติ (กรองตามเป้าหมายได้)
./omega-check.sh history --target 192.168.1.10 --limit 20

# รายละเอียดการสแกน (ข้อความ, JSON หรือ HTML) — เลือกธีมการส่งออกได้ 5 แบบ
./omega-check.sh show <scan_id> --format html --theme omega-base --output report.html

# เปรียบเทียบการสแกนสองครั้ง (การเปลี่ยนสถานะพอร์ต)
./omega-check.sh compare <scan_id_a> <scan_id_b>

# โปรไฟล์พอร์ตส่วนตัว
./omega-check.sh profile list
./omega-check.sh profile create lab --ports 22,80,443 --description "โปรไฟล์ของฉัน"
./omega-check.sh profile edit lab --ports 22,80,443,8080
./omega-check.sh profile pin lab
./omega-check.sh profile unpin lab
./omega-check.sh profile delete lab
```

### รูปแบบเป้าหมายที่รับได้

```text
192.168.1.10                IPv4
example.org                 ชื่อโฮสต์
http://example.org          URL แบบ HTTP  (ตัดโปรโตคอลออกก่อนแปลงชื่อ)
https://example.org:8443    URL แบบ HTTPS พร้อมพอร์ต  (ตัดโปรโตคอลและพอร์ตออก)
```

โปรโตคอลและพอร์ต (ถ้ามี) จะถูกตัดออกก่อนแปลงชื่อ DNS (`domain/targets/validation.py::normalize_target_input`) — วาง URL ทั้งหมดก็ใช้ได้ ระบบจะเก็บไว้เฉพาะโฮสต์

## 5. สถาปัตยกรรม

Omega-check จัดโครงสร้างตาม **Clean Architecture** (domain / application / infrastructure / interfaces / ports / core / app / plugins / shared) สอดคล้องกับแม่แบบของชุด `omega-` (ดู `omega-scan`/`omega-stress`) และตรวจสอบด้วย `import-linter` ทุกครั้งที่แก้ไข รายละเอียดทั้งหมดอยู่ใน **`docs/ARCHITECTURE.md`**

ภาพรวมแบบสั้นมาก:

```text
src/omega_check/
├── domain/          ตรรกะทางธุรกิจล้วน (การสแกน เป้าหมาย บริการ โปรไฟล์ รายงาน...)
├── application/     กรณีการใช้งาน (commands/queries)
├── ports/           สัญญาที่แอปพลิเคชันคาดหวัง (ตัวตรวจ ที่เก็บข้อมูล ตัวส่งออก...)
├── infrastructure/  การทำงานจริง (socket/httpx/cryptography, SQLite; Textual ไม่ได้อยู่ที่นี่)
├── interfaces/      tui/ (Textual) และ cli/ (เขียนสคริปต์ได้) ความสามารถเท่ากันอย่างเคร่งครัด
├── app/             การประกอบ (DependencyContainer, bootstrap, วงจรชีวิต)
├── core/, shared/   คำศัพท์ร่วม เครื่องมือที่ไม่เกี่ยวกับธุรกิจ
└── plugins/         วางโครงสร้างไว้แล้ว ยังว่าง (ยังไม่มีแนวทางขยายที่ยืนยันแล้ว)
```

กฎการออกแบบ:
- `domain/services/policies.py`: จัดประเภทเบาะแสที่เก็บได้แล้ว ไม่เข้าถึงเครือข่ายเลย
- `infrastructure/network/`: ทำงานกับเครือข่าย (ซ็อกเก็ต, `httpx`, `cryptography`) ไม่ตัดสินใด ๆ
- `interfaces/`: แสดงผล ไม่มีตรรกะทางธุรกิจ
- `infrastructure/exporters/`: อ่านผลการสแกน ไม่คำนวณสิ่งใดใหม่

## 6. การระบุบริการและบทบาท

### โปรโตคอลที่ตรวจพบ

| โปรโตคอล | วิธีตรวจ | รายละเอียดที่เก็บ |
|---|---|---|
| HTTP / HTTPS | `httpx` | แบนเนอร์ `Server` ส่วนหัวการยืนยันตัวตน |
| TLS | `cryptography` (ใบรับรองที่เจรจาได้ รวมถึง `CERT_NONE`) | เวอร์ชัน ชุดการเข้ารหัส ผู้ถือ/ผู้ออกใบรับรอง |
| SSH | แบนเนอร์ดิบ | ซอฟต์แวร์และเวอร์ชัน (เช่น `OpenSSH 10.4`) |
| VNC (RFB) | รหัสความปลอดภัยที่เซิร์ฟเวอร์ประกาศ | ประเภทการยืนยันตัวตนที่รองรับ |
| ทั่วไป | แบนเนอร์ดิบบนพอร์ตที่เปิดแต่ไม่รู้จัก | ดึงข้อมูลอย่างระมัดระวัง ไม่ใช้ฮิวริสติกที่รุนแรง |

### บทบาทที่อนุมาน

อนุมานจากโปรโตคอลที่ **เจรจาได้จริง** ไม่ใช่การเดาจากหมายเลขพอร์ต:

| บทบาท | เงื่อนไข | ความเชื่อมั่น |
|---|---|---|
| `เว็บเซิร์ฟเวอร์` | ยืนยันโปรโตคอล HTTP/HTTPS แล้ว | `INFERRED` |
| `การเข้าถึงเชลล์` | ยืนยันโปรโตคอล SSH แล้ว | `CORROBORATED` |
| `การเข้าถึงแบบกราฟิก` | ยืนยันโปรโตคอล VNC แล้ว | `CORROBORATED` |
| `ฐานข้อมูล` | พอร์ตอยู่ในช่วงของโปรไฟล์ระบบ `db` | `INFERRED` |

### ลายเซ็น WAF ที่รู้จัก

ตรวจพบผ่านส่วนหัวเชิงประกาศ (`server`, `x-sdk`) — การมีอยู่ **ประกาศโดยเป้าหมายเอง** ไม่เคยตรวจสอบโดยอิสระ: Cloudflare, Sucuri, Akamai, Imperva Incapsula, AWS ELB (ระบุไว้เพื่อเป็นข้อมูล ไม่ได้เป็น WAF ระดับแอปพลิเคชันโดยแท้)

## 7. นโยบายความเชื่อมั่น

ทุกช่องข้อมูลที่เก็บได้จะมีระดับใดระดับหนึ่งต่อไปนี้:

| ระดับ | ความหมาย |
|---|---|
| `VERIFIED` | ข้อเท็จจริงของโปรโตคอลที่สังเกตได้โดยตรง เป้าหมายปลอมแปลงไม่ได้ (เช่น พอร์ตปิดที่ยืนยันด้วย TCP RST เวอร์ชัน TLS ที่เจรจาได้จริง) |
| `DECLARED` | ค่าที่เป้าหมายประกาศเองในช่องที่ควบคุมได้ทั้งหมด (เช่น แบนเนอร์ `Server`) — ดูน่าเชื่อแต่ปลอมแปลงได้ตามใจ |
| `CORROBORATED` | ค่า `DECLARED` ที่ได้รับการยืนยันจากเบาะแสอิสระ (เช่น บทบาท SSH เพราะโปรโตคอลเจรจาได้จริง) |
| `INFERRED` | อนุมานจากรูปแบบ/ฮิวริสติก โดยเป้าหมายไม่ได้ประกาศอย่างชัดเจน |
| `UNKNOWN` | ไม่มีเบาะแสที่ใช้ได้ หรือเป้าหมายจงใจซ่อน |

## 8. การป้องกันค่าที่ถูกปลอมแปลง

Omega-check ไม่เชื่อข้อมูลใดที่เป้าหมายประกาศเองโดยไม่ระบุอย่างชัดเจน แบนเนอร์ `Server` หรือส่วนหัว `X-Powered-By` ยังคงเป็น `DECLARED` ไม่ใช่ `VERIFIED` ไม่ว่าจะดูน่าเชื่อเพียงใด — เพราะเป้าหมายเป็นผู้ให้ข้อมูลเหล่านี้เองและปลอมแปลงได้ตามใจ มีเพียงการยืนยันผ่านช่องทางอิสระ (เช่น โปรโตคอล SSH ที่เจรจาได้จริงสำหรับบทบาท “การเข้าถึงเชลล์”) เท่านั้นที่ยกระดับข้อมูลเป็น `CORROBORATED` การแยกแยะนี้อยู่ใน `omega-lib` (`ConfidenceLevel`) และเป็นเชิงโครงสร้าง: ไม่มีการส่งออกหรือมุมมองใดซ่อนมันได้

## 9. ความเข้ากันได้กับเทอร์มินัล

TUI (Textual) ตรวจจับความสามารถของเทอร์มินัล (อีมูเลเตอร์ ขนาด) โดยอัตโนมัติ และปรับสไตล์ชีตเชิงโครงสร้างให้เหมาะสม (`complete`/`standard`/`reduced`/`mono`) โดยไม่ต้องตั้งค่าเอง โหมด CLI เป็นข้อความธรรมดาเสมอ ไม่ขึ้นกับเทอร์มินัล เป็นนโยบายที่ใช้ร่วมกันทั้งชุด `omega-` (`omega-lib`, `terminal/policies.py`)

### โปรไฟล์ตามอีมูเลเตอร์ที่ตรวจพบ

| อีมูเลเตอร์ | โปรไฟล์เริ่มต้น |
|---|---|
| Ghostty, Alacritty, WezTerm, Kitty | `complete` |
| Konsole, GNOME Terminal, Terminator, Xfce4 Terminal | `standard` |
| xterm, urxvt, SSH รุ่นใหม่ | `reduced` |
| TTY ของ Linux, SSH รุ่นเก่า | `mono` |
| อีมูเลเตอร์ที่ไม่รู้จัก | `reduced` (ค่าสำรองเริ่มต้น) |

### โปรไฟล์ตามขนาดเทอร์มินัล

| ขนาดขั้นต่ำ (คอลัมน์ × บรรทัด) | เพดานโปรไฟล์ |
|---|---|
| 120 × 32 | `complete` |
| 100 × 28 | `standard` |
| 80 × 24 | `reduced` |
| ต่ำกว่านั้น | `mono` |

โปรไฟล์สุดท้ายคือ **โปรไฟล์ที่เข้มงวดกว่าในสองแบบ** (อีมูเลเตอร์และขนาด) — Ghostty แบบเต็มจอที่ถูกย่อเหลือ 70 คอลัมน์จะลดลงเป็น `mono` แม้อีมูเลเตอร์จะรองรับ `complete` ก็ตาม รีเฟรชสดได้ด้วยแป้น `r`

## 10. การส่งออก

รายงานข้อความและ HTML เขียนด้วยภาษาที่เลือกในการตั้งค่า (“ภาษาของการส่งออก” ค่าเริ่มต้นคือภาษาของอินเทอร์เฟซ) ส่วน JSON ยังคงเป็นข้อมูลและไม่ถูกแปล รายงานถูกสร้างใน `var/exports/` เป็นค่าเริ่มต้น (เส้นทางขณะทำงานยึดกับโฟลเดอร์โปรเจกต์ ใช้ `$OMEGA_CHECK_VAR_DIR` เพื่อเปลี่ยน) หรือที่เส้นทางที่ระบุ (`--output` ใน CLI กล่องโต้ตอบใน TUI) ชื่อไฟล์ชัดเจนและมีเวลากำกับ: `scan-{โปรไฟล์}-{วันที่}.ext`, `scan-custom-{วันที่}.ext` สำหรับโปรไฟล์ส่วนตัว และ `scan-{วันที่}.ext` สำหรับการกรอกเองโดยไม่มีโปรไฟล์

### JSON แหล่งข้อมูลหลัก

โครงสร้างทั้งหมดของการสแกน (`Scan` + `Host`) แปลงเป็น JSON ได้อย่างเคร่งครัด รวมระดับความเชื่อมั่น

### ข้อความ รายงานกะทัดรัดสำหรับอ่าน

อ่านได้นอกเทอร์มินัล ไม่มีรหัส ANSI

### HTML รายงานเว็บแบบสมบูรณ์ในตัว

เลือกได้ 5 ธีม (`--theme` ใน CLI ตัวเลือกใน TUI; ค่าเริ่มต้นจะตามธีมอินเทอร์เฟซที่ใช้อยู่หากมีธีมที่ตรงกัน) เลย์เอาต์เฉพาะ: คอนเทนเนอร์ ตารางข้อมูล กล่องสถิติตามสถานะพอร์ต ป้ายสี — อยู่ในตระกูลภาพเดียวกับ `omega-scan`/`omega-stress`

## 11. ประวัติและการเปรียบเทียบ

ทุกการสแกนถูกบันทึกไว้ (SQLite, `var/db/omega-check.db`): เปิดดูประวัติตามเป้าหมายได้ ดูรายละเอียดการรันที่ผ่านมา เปรียบเทียบการสแกนสองครั้ง (สถานะพอร์ต) และเรียกสแกนซ้ำกับเป้าหมายเดิมโดยไม่ต้องกรอกใหม่
