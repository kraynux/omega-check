**Omega-check** — инструмент с TUI и CLI, который сканирует порты одной сетевой цели, определяет службу на каждом открытом порту (протокол, программа, версия, аутентификация, WAF, TLS) и выводит её вероятную роль, никогда не проводя активной атаки. Инструмент набора `omega-`, построенный по принципам Clean Architecture — все технические подробности см. в `docs/ARCHITECTURE.md`.

## 1. Назначение и границы

Omega-check — сканер портов для системного администрирования: быстро проверить, что слушает на машине (своей, в локальной сети или на разрешённой внешней цели), чем именно, и насколько можно доверять каждому полученному сведению.

### Что делает Omega-check

- Сканирует список портов (системный профиль, личный профиль или свободный ввод) на одной цели.
- Определяет службу на каждом открытом порту: протокол (HTTP/HTTPS/SSH/TLS/VNC/общий), программу и версию, если они видны, требование аутентификации.
- Выводит вероятную роль (веб-сервер, доступ к оболочке, графический доступ, база данных) из протокола, действительно согласованного при соединении, и никогда — из простого предположения по номеру порта.
- Обнаруживает известные сигнатуры WAF (Cloudflare, Sucuri, Akamai, Imperva Incapsula), когда они объявлены в заголовках.
- Показывает результат в TUI (Textual) или в CLI для сценариев и в трёх видах экспорта: JSON, текст, HTML (5 тем).
- Присваивает каждому собранному сведению явный уровень доверия — см. [§7](#7-политика-доверия).
- Хранит постоянную историю сканирований, которые можно повторять и сравнивать во времени.
- Позволяет закреплять цели и создавать личные профили портов, которые можно использовать от сканирования к сканированию.

### Чего Omega-check не делает

- Активное сканирование уязвимостей: никаких SQLi, XSS или RCE.
- Сканирование CVE.
- Определение операционной системы (в модели данных поле предусмотрено, но пока ни одна эвристика его не заполняет).
- Низкоуровневые техники сканирования в духе nmap (SYN-сканирование, сырые пакеты) — только TCP-соединения прикладного уровня.
- Перебор паролей или фаззинг.
- Параллельное сканирование нескольких целей.
- Веб-панель.

## 2. Установка

### Требования

- Python 3.10+
- Подключение к Интернету, для зависимостей

### Установка

```bash
[ -d omega-check ] && echo "ℹ️ Уже распаковано здесь, шаг пропущен." || tar -xzf omega-check.tar.gz
cd omega-check/
chmod +x install.sh
./install.sh
```

`install.sh`:

1. Создаёт виртуальное окружение `.venv`, если его ещё нет.
2. Устанавливает зависимости (`pip install -e .`; `pyproject.toml` остаётся единственным источником истины).
3. Делает `omega-check.sh` и `install.sh` исполняемыми.
4. Добавляет псевдоним `check` в `~/.bashrc` и `~/.zshrc` (без дублирования, если он уже есть).

### Зависимости

Объявлены в `pyproject.toml` (`requirements.txt` больше нет):
- `omega-lib`: общая библиотека набора (`ConfidenceLevel`, темы, определение терминала)
- `textual`: интерфейс TUI, темы, автоматическая подстройка под терминал
- `httpx`: зонд HTTP/HTTPS
- `cryptography`: чтение согласованного сертификата TLS
- `jinja2`: шаблоны для экспорта в HTML
- Зависимости для разработки (`pip install -e ".[dev]"`): `pytest`, `pytest-asyncio`, `pytest-cov`, `pytest-httpserver`, `trustme`, `ruff`, `mypy`, `import-linter`

## 3. Использование

### Интерактивный режим (TUI)

Рекомендуется для повседневной работы — запускается без аргументов:

```bash
./omega-check.sh
```
если вы создали псевдоним, просто наберите `check` в терминале:
```bash
check
```

Порядок работы: заставка (закрывается нажатием клавиши или щелчком) → главное меню (Сканировать / Цели / Профили / История / Настройки / Справка) → ввод цели (с выбором закреплённых целей) и выбор профиля (предупреждение для `complet`, второе поле для личного профиля или свободного ввода портов при `CUSTOM`) → сканирование (неопределённый индикатор и журнал сетевых операций в реальном времени) → подробности сканирования (порты/службы/роли, экспорт) → история/сравнение/повтор и настройки из главного меню. Подстройка под терминал (цвета, размер, упрощение структуры) происходит автоматически.

#### Сочетания клавиш

| Клавиша | Действие |
|---|---|
| `↑` / `↓` | Переход между элементами экрана |
| `Tab` / `Shift+Tab` | Переход между полями формы |
| `Esc` | Возврат на предыдущий экран (подтверждение выхода на главном экране) |
| `t` | Следующая тема (применяется сразу, без подтверждения) |
| `r` | Обновить определение терминала |
| `a` | Показать справку |
| `q` | Выйти (с подтверждением) |

### Языки интерфейса

Интерфейс доступен на 17 языках: французском, английском, испанском, португальском (Бразилия), итальянском, немецком, нидерландском, польском, русском, упрощённом китайском, вьетнамском, тайском, индонезийском, японском, корейском, хинди и арабском. Язык выбирается в Настройках («Langue / Language») и применяется после перезапуска интерфейса; переменная `OMEGA_CHECK_LANG` (например, `OMEGA_CHECK_LANG=ru ./omega-check.sh`) задаёт язык на один сеанс. При запуске из omega-suite omega-check использует язык набора. В текстовой консоли Linux (TTY) языки с нелатинской письменностью на время сеанса показываются по-английски. Командная строка остаётся на французском.

### Контакты и поддержка

Справка (клавиша `a`) предлагает экран **Контакты и поддержка**: *Угостить кофе* (страница PayPal разработчика), *Связаться с поддержкой* (адрес электронной почты и контактная форма сайта, показанные открыто), *Зарегистрироваться как пользователь (анонимно)* и *Проверить обновления*. Регистрация добровольная, по умолчанию отключена и отправляется только один раз: она служит лишь для подсчёта пользователей и, по желанию, их континента или страны (закрытые списки, никогда не свободный текст). Отправляются случайно сгенерированный ключ, название программы (`omega-check`) и её версия; никогда имя, имя машины, настройка, цель или результат. IP-адрес не сохраняется в регистрациях, но, как при любом посещении, проходит через проверки безопасности и журнал принимающего сервера. Отозвать регистрацию можно в любой момент на том же экране (*Больше не регистрировать меня*). Проверка обновлений лишь читает список версий, опубликованных на сайте, и никогда без щелчка.

### Режим для сценариев (CLI)

Любая подкоманда включает режим CLI:

```bash
# Сканировать цель с профилем портов
./omega-check.sh scan 192.168.1.10 --profile minimal

# История (с фильтром по цели)
./omega-check.sh history --target 192.168.1.10 --limit 20

# Подробности сканирования (текст, JSON или HTML) — на выбор 5 тем экспорта
./omega-check.sh show <scan_id> --format html --theme omega-base --output otchet.html

# Сравнить два сканирования (изменения состояния портов)
./omega-check.sh compare <scan_id_a> <scan_id_b>

# Личные профили портов
./omega-check.sh profile list
./omega-check.sh profile create lab --ports 22,80,443 --description "Мой профиль"
./omega-check.sh profile edit lab --ports 22,80,443,8080
./omega-check.sh profile pin lab
./omega-check.sh profile unpin lab
./omega-check.sh profile delete lab
```

### Допустимые форматы цели

```text
192.168.1.10                IPv4
example.org                 Имя хоста
http://example.org          URL HTTP  (схема удаляется до разрешения имени)
https://example.org:8443    URL HTTPS с портом  (схема и порт удаляются)
```

Схема и порт, если они есть, удаляются до разрешения DNS (`domain/targets/validation.py::normalize_target_input`) — можно вставить URL целиком, сохраняется только хост.

## 5. Архитектура

Omega-check построен по принципам **Clean Architecture** (domain / application / infrastructure / interfaces / ports / core / app / plugins / shared), согласованным с шаблоном набора `omega-` (см. `omega-scan`/`omega-stress`), и проверяется `import-linter` при каждом изменении. Все подробности — в **`docs/ARCHITECTURE.md`**.

Очень краткий обзор:

```text
src/omega_check/
├── domain/          Чистая предметная логика (сканирования, цели, службы, профили, отчёты...)
├── application/     Сценарии использования (commands/queries)
├── ports/           Контракты, ожидаемые приложением (зонды, репозитории, экспортёры...)
├── infrastructure/  Конкретные реализации (socket/httpx/cryptography, SQLite; Textual здесь НЕТ)
├── interfaces/      tui/ (Textual) и cli/ (для сценариев), со строгим равенством возможностей
├── app/             Сборка (DependencyContainer, bootstrap, жизненный цикл)
├── core/, shared/   Общий словарь, вспомогательные средства вне предметной логики
└── plugins/         Структура заложена, пуста (ни одно направление расширения не подтверждено)
```

Правила проектирования:
- `domain/services/policies.py`: классифицирует уже собранные признаки, никогда не обращается к сети.
- `infrastructure/network/`: работает с сетью (сокеты, `httpx`, `cryptography`), никогда не выносит оценок.
- `interfaces/`: отображает, не содержит предметной логики.
- `infrastructure/exporters/`: читают результат сканирования, ничего не пересчитывают.

## 6. Определение служб и роли

### Обнаруживаемые протоколы

| Протокол | Зонд | Собираемые сведения |
|---|---|---|
| HTTP / HTTPS | `httpx` | Баннер `Server`, заголовки аутентификации |
| TLS | `cryptography` (согласованный сертификат, включая `CERT_NONE`) | Версия, шифр, субъект/издатель сертификата |
| SSH | Сырой баннер | Программа и версия (например, `OpenSSH 10.4`) |
| VNC (RFB) | Коды безопасности, объявленные сервером | Поддерживаемые типы аутентификации |
| Общий | Сырой баннер на нераспознанном открытом порту | Осторожное извлечение, без агрессивной эвристики |

### Выводимые роли

Выводятся из **действительно согласованного** протокола, никогда — из предположения по номеру порта:

| Роль | Условие | Доверие |
|---|---|---|
| `веб-сервер` | Протокол HTTP/HTTPS подтверждён | `INFERRED` |
| `доступ к оболочке` | Протокол SSH подтверждён | `CORROBORATED` |
| `графический доступ` | Протокол VNC подтверждён | `CORROBORATED` |
| `база данных` | Порт в диапазоне системного профиля `db` | `INFERRED` |

### Известные сигнатуры WAF

Обнаруживаются по декларативному заголовку (`server`, `x-sdk`) — присутствие **объявлено самой целью** и никогда не проверяется независимо: Cloudflare, Sucuri, Akamai, Imperva Incapsula, AWS ELB (указан для сведения, строго говоря не является прикладным WAF).

## 7. Политика доверия

Каждое собранное поле имеет один из уровней:

| Уровень | Значение |
|---|---|
| `VERIFIED` | Протокольный факт, наблюдаемый напрямую, который цель не может подделать (например, закрытый порт, подтверждённый TCP RST, действительно согласованная версия TLS). |
| `DECLARED` | Значение, объявленное самой целью в поле, которое она полностью контролирует (например, баннер `Server`), — правдоподобно, но подделывается как угодно. |
| `CORROBORATED` | Значение `DECLARED`, подтверждённое независимым признаком (например, роль SSH, поскольку протокол действительно был согласован). |
| `INFERRED` | Выведено из шаблона/эвристики, без явного объявления со стороны цели. |
| `UNKNOWN` | Нет пригодных признаков, или цель активно их скрывает. |

## 8. Защита от поддельных значений

Omega-check не доверяет никаким данным, объявленным самой целью, не помечая этого явно. Баннер `Server` или заголовок `X-Powered-By` остаются `DECLARED`, никогда `VERIFIED`, как бы правдоподобно они ни выглядели, — их выдаёт сама цель и может подделать как угодно. Только подтверждение по независимому каналу (например, действительно согласованный протокол SSH для роли «доступ к оболочке») переводит сведение в `CORROBORATED`. Это различие, заложенное в `omega-lib` (`ConfidenceLevel`), структурно: ни один экспорт и ни одно представление не могут его скрыть.

## 9. Совместимость с терминалами

TUI (Textual) автоматически определяет возможности терминала (эмулятор, размер) и соответственно подстраивает свою структурную таблицу стилей (`complete`/`standard`/`reduced`/`mono`), без ручных параметров. Режим CLI всегда остаётся простым текстом, независимо от терминала. Это правило общее для всего набора `omega-` (`omega-lib`, `terminal/policies.py`).

### Профиль по определённому эмулятору

| Эмулятор | Начальный профиль |
|---|---|
| Ghostty, Alacritty, WezTerm, Kitty | `complete` |
| Konsole, GNOME Terminal, Terminator, Xfce4 Terminal | `standard` |
| xterm, urxvt, современный SSH | `reduced` |
| TTY Linux, старый SSH | `mono` |
| Нераспознанный эмулятор | `reduced` (запасной вариант по умолчанию) |

### Профиль по размеру терминала

| Минимальный размер (столбцы × строки) | Верхний предел профиля |
|---|---|
| 120 × 32 | `complete` |
| 100 × 28 | `standard` |
| 80 × 24 | `reduced` |
| меньше | `mono` |

Итоговый профиль — **более строгий из двух** (эмулятор и размер): Ghostty на весь экран, уменьшенный до 70 столбцов, опускается до `mono`, хотя его эмулятор позволил бы `complete`. Обновляется на лету клавишей `r`.

## 10. Экспорт

Текстовые и HTML-отчёты пишутся на языке, выбранном в Настройках («Язык экспорта», по умолчанию — язык интерфейса); JSON остаётся данными и не переводится. По умолчанию отчёты создаются в `var/exports/` (рабочий путь привязан к папке проекта, `$OMEGA_CHECK_VAR_DIR` позволяет его переопределить) или по указанному пути (`--output` в CLI, диалоговое окно в TUI). Понятное имя файла с отметкой времени: `scan-{профиль}-{дата}.ext`, `scan-custom-{дата}.ext` для личного профиля, `scan-{дата}.ext` для свободного ввода без профиля.

### JSON — источник истины

Полная структура сканирования (`Scan` + `Host`), строго сериализуемая в JSON, включая уровни доверия.

### Текст — компактный отчёт для чтения

Читается вне терминала, без кодов ANSI.

### HTML — самостоятельный веб-отчёт

5 тем на выбор (`--theme` в CLI, переключатель в TUI; по умолчанию следует активной теме интерфейса, если есть соответствие). Собственная вёрстка: контейнер, сетка сведений, блоки статистики по состоянию портов, цветные значки — то же визуальное семейство, что у `omega-scan`/`omega-stress`.

## 11. История и сравнение

Каждое сканирование сохраняется (SQLite, `var/db/omega-check.db`): история по цели, подробности прошлого запуска, сравнение двух сканирований (состояние портов) и повтор сканирования той же цели без повторного ввода.
