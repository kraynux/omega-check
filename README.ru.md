**Omega-check** — инструмент TUI + CLI, который сканирует порты одной сетевой цели, определяет сервис на каждом открытом порту (протокол, ПО, версия, аутентификация, WAF, TLS) и выводит предполагаемую роль, не выполняя активных атак. Это четвёртый инструмент набора `omega-` (после `omega-fire`, `omega-stress` и `omega-scan`), организованный по принципам Clean Architecture; полное техническое описание см. в `docs/ARCHITECTURE.md`.

## 1. Назначение и границы

Omega-check — сканер портов для системного администрирования: он быстро проверяет, что слушает на машине (на вашей, в LAN или на разрешённой внешней цели), какой сервис за этим стоит и насколько достоверна каждая собранная характеристика.

### Что делает Omega-check

- Сканирует список портов (системный профиль, пользовательский профиль или произвольный ввод) на одной цели.
- Определяет сервис на каждом открытом порту: протокол (HTTP/HTTPS/SSH/TLS/VNC/общий), ПО и версию, если они раскрыты, а также необходимость аутентификации.
- Выводит предполагаемую роль (веб-сервер, shell-доступ, графический доступ, база данных) по фактически согласованному протоколу, а не по простому предположению о номере порта.
- Обнаруживает известные сигнатуры WAF (Cloudflare, Sucuri, Akamai, Imperva Incapsula), если они заявлены в заголовках.
- Показывает результат в TUI на Textual или скриптуемом CLI и экспортирует его в JSON, текст и HTML (5 тем).
- Присваивает каждой собранной характеристике явный уровень доверия; см. [§7](#7-политика-доверия).
- Хранит постоянную историю сканирований, доступную для повторного запуска и сравнения во времени.
- Поддерживает закреплённые цели и пользовательские профили портов, повторно используемые в разных сканированиях.

### Чего Omega-check не делает

- Не выполняет активное сканирование уязвимостей, SQLi, XSS или RCE.
- Не сканирует CVE.
- Не выполняет fingerprinting операционной системы (поле предусмотрено моделью данных, но пока не заполняется эвристикой).
- Не использует низкоуровневые методы наподобие nmap (SYN-сканирование, сырые пакеты): только прикладные TCP-соединения.
- Не является инструментом bruteforce или fuzzing.
- Не выполняет параллельное сканирование нескольких целей.
- Не предоставляет веб-панель.

## 2. Установка

### Требования

- Python 3.10+
- Подключение к Интернету для зависимостей

### Установка

```bash
[ -d omega-check ] && echo "ℹ️ Уже распаковано здесь, шаг пропущен." || tar -xzf omega-check.tar.gz
cd omega-check/
chmod +x install.sh
./install.sh
```

`install.sh`:

1. Создаёт `.venv`, если виртуальное окружение ещё не существует.
2. Устанавливает зависимости (`pip install -e .`; `pyproject.toml` остаётся единственным источником истины).
3. Делает `omega-check.sh` и `install.sh` исполняемыми.
4. Добавляет алиас `check` в `~/.bashrc` и `~/.zshrc`, не создавая дубликат.

### Зависимости

Указаны в `pyproject.toml` (файл `requirements.txt` больше не используется):
- `omega-lib`: общая библиотека набора (`ConfidenceLevel`, темы, определение терминала).
- `textual`: TUI, темы и автоматическая адаптация к терминалу.
- `httpx`: HTTP/HTTPS-проба.
- `cryptography`: чтение согласованного TLS-сертификата.
- `jinja2`: шаблоны для HTML-экспорта.
- Зависимости разработки (`pip install -e ".[dev]"`): `pytest`, `pytest-asyncio`, `pytest-cov`, `pytest-httpserver`, `trustme`, `ruff`, `mypy`, `import-linter`.

## 3. Использование

### Интерактивный режим (TUI)

Рекомендуется для ежедневной работы; запускается без аргументов:

```bash
./omega-check.sh
```

Если алиас создан, достаточно ввести в терминале:

```bash
check
```

Сценарий: стартовый экран (закрывается клавишей или щелчком) → главное меню (Сканер / Цели / Профили / История / Настройки / Справка) → ввод цели (с выбором закреплённых целей) и профиля (предупреждение для `complet`, второе поле для пользовательского профиля или произвольный ввод портов для `CUSTOM`) → сканирование (индикатор неопределённого прогресса и сетевые операции в реальном времени) → подробности (порты/сервисы/роли, экспорт) → история, сравнение, повторный запуск и настройки из главного меню. Адаптация к терминалу (цвета, размер и структурное упрощение) выполняется автоматически.

#### Горячие клавиши

| Клавиша | Действие |
|---|---|
| `↑` / `↓` | Перемещение между элементами экрана |
| `Tab` / `Shift+Tab` | Перемещение между полями формы |
| `Esc` | Возврат к предыдущему экрану (на главном экране подтверждается выход) |
| `t` | Следующая тема (применяется сразу, без подтверждения) |
| `r` | Обновить определение терминала |
| `a` | Показать справку |
| `q` | Выйти с подтверждением |

### Скриптуемый режим (CLI)

Любая подкоманда запускает CLI:

```bash
# Сканировать цель с профилем портов
./omega-check.sh scan 192.168.1.10 --profile minimal

# История (фильтрация по цели)
./omega-check.sh history --target 192.168.1.10 --limit 20

# Подробности сканирования (текст, JSON или HTML), доступно 5 тем экспорта
./omega-check.sh show <scan_id> --format html --theme omega-base --output report.html

# Сравнить два сканирования (изменения состояний портов)
./omega-check.sh compare <scan_id_a> <scan_id_b>

# Пользовательские профили портов
./omega-check.sh profile list
./omega-check.sh profile create lab --ports 22,80,443 --description "Мой профиль"
./omega-check.sh profile edit lab --ports 22,80,443,8080
./omega-check.sh profile pin lab
./omega-check.sh profile unpin lab
./omega-check.sh profile delete lab
```

### Допустимые форматы цели

```text
192.168.1.10                IPv4
example.org                 Имя хоста
http://example.org          URL HTTP (схема удаляется перед разрешением)
https://example.org:8443    URL HTTPS с портом (схема и порт удаляются)
```

Схема и возможный порт удаляются до DNS-разрешения (`domain/targets/validation.py::normalize_target_input`): можно вставить полный URL, будет сохранён только хост.

## 4. Профили сканирования

| Профиль | Описание | Закреплён |
|---|---|---|
| `minimal` | Очень быстрое сканирование: SSH + HTTP + HTTPS (22, 80, 443) | да |
| `classic` | Классические сервисы Интернета/LAN (37 портов) | да |
| `web` | Веб-сервисы и альтернативные порты | нет |
| `db` | Базы данных и сервисы данных | нет |
| `remote` | Удалённый доступ: shell, рабочий стол, RustDesk | нет |
| `mail` | Почтовые сервисы | нет |
| `dns` | DNS-сервисы | нет |
| `iot` | IoT-оборудование, камеры, шлюзы и умный дом | нет |
| `dev` | Среды разработки и лаборатории | нет |
| `docker` | Docker, Swarm и распространённые контейнерные сервисы | нет |
| `complet` | **Генерируется на лету**: отсортированное объединение без дубликатов всех профилей выше | нет |
| `CUSTOM` | Пользовательский профиль из **Профили** и/или произвольный ввод (`80` / `22,443,8080` / `1000-2000`); оба источника объединяются без дубликатов | нет |

Полное описание, правила проверки и управление пользовательскими профилями: `docs/PROFILES.md`.

## 5. Архитектура

Omega-check организован по принципам **Clean Architecture** (domain / application / infrastructure / interfaces / ports / core / app / plugins / shared), соответствует шаблону набора `omega-` (см. `omega-scan`/`omega-stress`) и проверяется `import-linter` после каждого изменения. Полное описание находится в **`docs/ARCHITECTURE.md`**.

```text
src/omega_check/
├── domain/          Чистая бизнес-логика (сканирование, цели, сервисы, профили, отчёты...)
├── application/     Варианты использования (commands/queries)
├── ports/           Контракты приложения (probers, repositories, exporters...)
├── infrastructure/  Реализации (socket/httpx/cryptography, SQLite; Textual находится НЕ здесь)
├── interfaces/      tui/ (Textual) и cli/ (скриптуемый), со строгим равенством функций
├── app/             Сборка (DependencyContainer, bootstrap, жизненный цикл)
├── core/, shared/   Общая терминология и утилиты, не относящиеся к бизнес-логике
└── plugins/         Подготовленная пустая структура (подтверждённых расширений нет)
```

Правила проектирования:
- `domain/services/policies.py`: классифицирует уже собранные признаки и никогда не выполняет сетевые операции.
- `infrastructure/network/`: выполняет сеть (sockets, `httpx`, `cryptography`), но никогда не принимает решения.
- `interfaces/`: отображает данные и не содержит бизнес-логики.
- `infrastructure/exporters/`: читает результат сканирования и ничего не пересчитывает.

## 6. Идентификация сервисов и ролей

### Обнаруживаемые протоколы

| Протокол | Проба | Собираемые данные |
|---|---|---|
| HTTP / HTTPS | `httpx` | Баннер `Server`, заголовки аутентификации |
| TLS | `cryptography` (согласованный сертификат, включая `CERT_NONE`) | Версия, cipher, subject/issuer сертификата |
| SSH | Необработанный баннер | ПО и версия (например, `OpenSSH 10.4`) |
| VNC (RFB) | Коды безопасности, объявленные сервером | Поддерживаемые типы аутентификации |
| Общий | Необработанный баннер открытого нераспознанного порта | Осторожное извлечение без агрессивной эвристики |

### Выводимые роли

Роли выводятся из **фактически согласованного протокола**, а не из предположительного номера порта:

| Роль | Условие | Доверие |
|---|---|---|
| `веб-сервер` | Подтверждён протокол HTTP/HTTPS | `INFERRED` |
| `shell-доступ` | Подтверждён протокол SSH | `CORROBORATED` |
| `графический доступ` | Подтверждён протокол VNC | `CORROBORATED` |
| `база данных` | Порт входит в диапазон системного профиля `db` | `INFERRED` |

### Известные сигнатуры WAF

Определяются по декларативным заголовкам (`server`, `x-sdk`); наличие **заявляется самой целью** и не проверяется независимо: Cloudflare, Sucuri, Akamai, Imperva Incapsula, AWS ELB (указан справочно и не является прикладным WAF в строгом смысле).

## 7. Политика доверия

Каждое собранное поле получает один из уровней:

| Уровень | Значение |
|---|---|
| `VERIFIED` | Непосредственно наблюдаемый протокольный факт, который цель не может подделать (например, закрытый порт, подтверждённый TCP RST, или фактически согласованная версия TLS). |
| `DECLARED` | Значение, самостоятельно объявленное целью в полностью контролируемом ею поле (например, баннер `Server`); правдоподобно, но может быть свободно подделано. |
| `CORROBORATED` | Значение `DECLARED`, подтверждённое независимым сигналом (например, роль SSH после фактического согласования протокола). |
| `INFERRED` | Вывод из шаблона или эвристики без явного объявления цели. |
| `UNKNOWN` | Нет полезных признаков или цель активно их скрывает. |

## 8. Защита от подделанных значений

Omega-check не доверяет автоматически данным, объявленным целью, и явно указывает это. Баннер `Server` или заголовок `X-Powered-By` остаётся `DECLARED`, а не `VERIFIED`, независимо от правдоподобия: их предоставляет сама цель и может подделать по своему желанию. Только подтверждение через независимый канал (например, фактически согласованный протокол SSH для роли «shell-доступ») повышает информацию до `CORROBORATED`. Это различие, реализованное в `omega-lib` (`ConfidenceLevel`), является структурным: ни экспорт, ни представление не могут его скрыть.

## 9. Совместимость с терминалами

TUI на Textual автоматически определяет возможности терминала (эмулятор и размер) и адаптирует структурную таблицу стилей (`complete`/`standard`/`reduced`/`mono`) без ручных флагов. CLI всегда остаётся обычным текстом и не зависит от терминала. Политика общая для набора `omega-` (`omega-lib`, `terminal/policies.py`).

### Профиль по эмулятору

| Эмулятор | Начальный профиль |
|---|---|
| Ghostty, Alacritty, WezTerm, Kitty | `complete` |
| Konsole, GNOME Terminal, Terminator, Xfce4 Terminal | `standard` |
| xterm, urxvt, современный SSH | `reduced` |
| Linux TTY, legacy SSH | `mono` |
| Неизвестный эмулятор | `reduced` (значение по умолчанию) |

### Профиль по размеру терминала

| Минимальный размер (столбцы × строки) | Максимальный профиль |
|---|---|
| 120 × 32 | `complete` |
| 100 × 28 | `standard` |
| 80 × 24 | `reduced` |
| меньше | `mono` |

Итоговый профиль — **наиболее ограничительный из двух** (эмулятор и размер). Ghostty в полноэкранном режиме, уменьшенный до 70 столбцов, перейдёт в `mono`, даже если сам эмулятор допускает `complete`. Обновляется в реальном времени клавишей `r`.

## 10. Экспорт

По умолчанию отчёты создаются в `var/exports/` (runtime-путь привязан к каталогу проекта; переопределяется через `$OMEGA_CHECK_VAR_DIR`) или по указанному пути (`--output` в CLI, диалог в TUI). Используются явные имена с временной меткой: `scan-{profile}-{date}.ext`, `scan-custom-{date}.ext` для пользовательского профиля и `scan-{date}.ext` для произвольного ввода без профиля.

### JSON — источник истины

Полная структура сканирования (`Scan` + `Host`), строго сериализуемая в JSON и содержащая уровни доверия.

### Текст — компактный отчёт

Читается вне терминала, без ANSI-кодов.

### HTML — автономный веб-отчёт

Доступно 5 тем (`--theme` в CLI или селектор в TUI; по умолчанию используется активная тема интерфейса, если есть эквивалент). Специальная компоновка с информационной сеткой, статистикой состояний портов и цветными бейджами в том же визуальном стиле, что и `omega-scan`/`omega-stress`.

## 11. История и сравнение

Каждое сканирование сохраняется в SQLite (`var/db/omega-check.db`): историю можно искать по цели, просматривать детали прошлого запуска, сравнивать два сканирования (состояния портов) и повторять сканирование той же цели без повторного ввода.

## 13. Вне области проекта

- Сканирование CVE.
- Активное обнаружение SQLi, XSS и RCE.
- Fingerprinting операционной системы.
- Низкоуровневые методы сканирования наподобие nmap (SYN-сканирование, сырые пакеты).
- Crawling.
- Fuzzing.
- Bruteforce.
- Одновременное сканирование нескольких целей.
- Веб-панель.
